# Safety Rules

These rules apply to all Codex work in this repo.

## Hard Rules

- Never work directly on `main` for feature work.
- Default is no push, no merge, and no deploy.
- Treat `push`, `push it`, `push now`, `push to main`, `send it live`, `release it`, or clear push/release approval as Safe Release Push Mode.
- Never push, merge, release, or deploy unless the full safe release pipeline passes.
- Never push `main` unless CEO confirms `SAFE TO RELEASE TO MAIN: YES`.
- Never deploy through Netlify unless CEO confirms `SAFE TO DEPLOY VIA NETLIFY: YES`.
- Never force push unless Yasir explicitly says force push and CEO confirms `SAFE TO FORCE PUSH: YES`.
- Never touch a live database without explicit Yasir approval for that exact action.
- Never touch secrets, `.env`, `.env.local`, API keys, tokens, or credential files.
- Never print secrets in logs, task notes, handovers, or transcript summaries.
- Never change auth, payment, database, environment, or deployment behavior without extra CEO approval.
- Never break the current working build for experimental work.
- Risky work must happen on a feature or hotfix branch.
- All changes must be verified before the CEO recommends push, merge, or deploy.

## Subagent Safety

- The main Codex chat is the command center.
- Spawn or use `yasir-ceo` first for every Yasir project command.
- `yasir-ceo` routes work to `debugger`, `developer`, `verifier`, and `auditor`.
- `developer` is the only role allowed to change code after CEO approval.
- `debugger`, `verifier`, and `auditor` must not edit application code.
- Subagents report back to CEO; CEO reports once to Yasir in the main chat.

## Risk Classification

High-risk work includes:

- Convex schema, queries, mutations, generated API, or deployment configuration.
- Fee, payment, amount due, course fee, or financial tracking logic.
- Netlify build, redirect, environment, or production deployment configuration.
- Authentication, identity, user access, or authorization behavior.
- Data export, backup, restore, delete, migration, seed, or bulk update logic.
- Package dependency, lockfile, build tooling, or runtime configuration changes.

## Branch Rules

- `main` is protected by process even if GitHub branch protection is not configured.
- Documentation-only setup may be created on `main` only when Yasir explicitly asks for repo operating-system files and no app code is touched.
- Feature, bug fix, refactor, database, auth, payment, or deployment work must happen on a feature or hotfix branch.
- Before changing files, check `git status --short --branch`.
- If unknown dirty changes exist, stop and ask Yasir unless they are clearly generated by the current approved task.

## Approval Rules

- CEO approval is required before Developer Agent changes code.
- Extra CEO approval is required for auth, payment, database, env, deployment, package, migration, seed, or production-impacting changes.
- Yasir approval is required before push, merge, PR creation when requested as final action, or deploy.
- A general `push` is a full safe release command to the normal release target, usually `main`.
- `push this branch only` or `push feature branch only` limits action to that branch and forbids main merge or production deploy.
- No agent can approve its own work.

## Safe Release Push Gates

Before any release push, CEO must verify correct project, branch, requested target, git status, git diff, changed files, risky files, secrets/env safety, auth/payment/database/env/deploy risk, available lint/tests/build/typecheck/route checks, verifier report, current build state, deployment risk, and rollback plan.

- `SAFE TO PUSH CURRENT BRANCH: YES/NO`
- `SAFE TO RELEASE TO MAIN: YES/NO`
- `SAFE TO DEPLOY VIA NETLIFY: YES/NO`
- `SAFE TO FORCE PUSH: YES/NO`
- `SAFE TO RELEASE/PUSH: YES/NO`

If any required gate is `NO`, do not push, merge, or deploy. CEO must explain why and what must be fixed first.

## Netlify Release Safety

- Pushing `main` may trigger production deploy.
- Pushing feature branches may trigger preview deploys.
- Treat main pushes as production-impacting unless `PROJECT_CONTEXT.md` says otherwise.
- If Netlify status cannot be checked, report `deployment verification blocked: Netlify access/status unavailable`.

## Verification Rules

- Run available checks that match the changed surface.
- For this repo, expected checks include `npm run lint` and `npm run build`.
- There is no dedicated test script detected in `package.json`; document that gap when reporting.
- Inspect `git diff` before final report.
- Confirm whether auth, payments, database, env, deployment, production data, or `main` were touched.
- For release pushes, include deployment status if tools/access are available.

## Secrets And Environments

- Do not open, edit, print, or commit `.env` or `.env.local` files.
- Environment variables are required for deployed Netlify/Convex behavior. If a missing value blocks work, stop and ask Yasir.
- Never add secrets to docs, code, logs, screenshots, or transcript summaries.
